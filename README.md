# Parallel Copy

A Windows Python window for copying folders through Robocopy or directly through
Google Drive's API using rclone. Source files and unrelated destination files stay
in place. This is a copy tool; it never mirrors, synchronizes deletions, or moves.

Double-click **Parallel Copy.pyw**, or run `python parallel_copy.py`.
Requires Python with Tkinter (standard Windows installer). No pip packages.

Open source under the [MIT License](LICENSE). Robocopy and rclone are separate
tools distributed under their respective licenses.

## Pick the correct route

- **Local…** chooses a Windows folder, including mounted Google Drive folders.
  Two Windows paths use Robocopy. `G:` uploads can continue after that command
  finishes: the completion message explicitly says so.
- **Drive…** chooses an authenticated Google Drive folder. One or two `gdrive:`
  paths use the direct API engine. Downloads bypass the desktop cache; uploads
  finish after Google acknowledges them; copies within the same Drive remote use
  server-side copying when supported. Folder contents remain normal files.
- **Copy into** is a parent folder. The source folder name is appended, and the
  resulting destination appears before starting.
- Existing files are kept by default. Enable **Replace existing files when
  different** to update a previously copied tree or restart an incomplete copy.
- **Stop** terminates the transfer process. Completed files remain, and partially
  transferred files can remain. Restart with replacement enabled. Restartable
  Robocopy affects Windows paths; rclone manages its own transfer behavior.

For cloud transfers, choose **Small files** for files concentrated in one folder,
**Many small files** for large trees spread across subfolders, or **Large files** for
larger payloads. The many-file preset uses direct downloads and independent folder
jobs for uploads/server-side copies. You can lower the worker count on a slower
computer or connection. More workers did not always improve measured performance.

See [PERFORMANCE.md](PERFORMANCE.md) for measured comparisons and limitations.

## Automatic cleanup

Each run owns a unique temporary directory for its log, rclone cache and temporary
files. After the transfer process exits, the window reads the final log and removes
that directory, including after Stop. The displayed log remains in memory until
you close the window. OAuth connection logs are also removed after they are read.
The rclone executable and saved login are retained because the app needs them.

Source files, completed destination files and Google's managed desktop cache are
never part of this cleanup. If a transfer is interrupted, partially written files
in the destination can remain for a later retry; the app does not guess which
pre-existing destination files are safe to delete. Completed transfers leave their
normal destination files in place.

## Direct Drive setup

Run `python install_rclone.py` once. It installs the official Windows build under
`.local/bin/` after verifying the publisher's SHA256 checksum. The measured
version is recorded with benchmark results; re-running installs the current build.

Use **Connect Drive…** with an OAuth desktop-client JSON from a Google Cloud
project with the Google Drive API enabled. Consent happens in Google's browser
page. The application requests Drive scope because it needs to read source files
and create destination files. The UI performs copy operations only.

The `gdrive` configuration and refresh token stay in ignored `.local/rclone.conf`.
Do not share that file or `.local/`. Existing Calendar credentials are neither
read nor changed by the copier. Moving this project preserves its local login;
cloning it elsewhere requires connecting again.

The folder picker currently browses My Drive. Shared-drive configurations can be
configured separately through rclone, but are outside this benchmark's coverage.
Duplicate folder names are refused by the picker; rename duplicates before using
path-based copying. Native Google Workspace files, shortcuts, shared-drive
permissions, and cross-account copies are not represented by the binary test set.

## Reproduce measurements

`python benchmark.py prepare` generates random binary test files under `.local/`.
`benchmark.py run --help` lists the measurement options. Run
`python benchmark.py seed` to upload and verify only the generated source fixtures
before testing downloads or cloud copies.
`python optimize.py` runs the initial serial comparison matrix. Each case has a
fresh destination; MD5 hashes and complete path sets must match to pass.

`results/measurements.jsonl` preserves successful and failed runs. The test folder
in Drive is `ParallelCopy-benchmark-20260913`; it contains generated bytes only.
No real user files are included in measurements. The harness does not automatically
delete test datasets while measurements are running. Afterward,
`python cleanup_benchmarks.py` archives logs, checks the generated cloud namespace,
permanently removes that benchmark folder, and verifies its absence. It refuses
unexpected top-level content or unrecorded run directories. Normal application
copies never invoke this benchmark-only deletion command.
Do not run normal copies alongside timed tests.
